# lar-em-dia-app

Flutter app (web, Android and iOS) for **Lar em Dia**, a family budgeting and cash-flow projection app. It consumes the Rails API in [lar-em-dia-api](https://github.com/gabrieltrita/lar-em-dia-api).

## Stack

| Concern | Package |
|---|---|
| State management | `flutter_bloc` (Cubit for simple screens, Bloc for event-driven flows), `bloc_test` |
| Routing | `go_router` |
| HTTP | `dio` with `AuthInterceptor` (Bearer token, refresh on 401, single retry) |
| Immutable models and JSON | `freezed`, `json_serializable`, `build_runner` |
| Dependency injection | `get_it` + `injectable` |
| Secure storage | `flutter_secure_storage` (refresh token in Keychain / Keystore; access token in memory only) |
| Localization | `flutter_localizations` + `intl`, ARB files in `lib/l10n` (pt-BR) |
| Charts | `fl_chart` |
| QR codes | `qr_flutter` (2FA enrollment) |
| Device time zone | `flutter_timezone` |
| Local notifications | `flutter_local_notifications` + `timezone` (due-date reminders on Android and iOS) |
| Lint | `very_good_analysis` |
| Tests | `flutter_test`, `mocktail`, `bloc_test` |

Flutter 3.47.9 (Dart 3.13).

## Getting started

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs
flutter run -d chrome --dart-define=API_BASE_URL=http://localhost:3000/api/v1
```

`API_BASE_URL` defaults to `http://localhost:3000/api/v1`. On the Android emulator the host machine is `10.0.2.2`, so use `--dart-define=API_BASE_URL=http://10.0.2.2:3000/api/v1`. The API must list the web origin in `CORS_ORIGINS`.

Generated files (`*.g.dart`, `*.freezed.dart`, `*.config.dart`, `lib/l10n/gen/`) are not committed: run `build_runner` after cloning and after changing annotated classes (`dart run build_runner watch -d` while developing). Localizations are generated by `flutter pub get` / `flutter gen-l10n`.

## API contract

- Successful responses are `{ "data": ..., "meta": ... }`; `ApiClient` returns them as `ApiResponse<T>`.
- Errors are `{ "error": { "code", "message", "details" } }`; `ApiClient` throws `ApiError`. Translate by `code` (and `details[field][].code`), never by `message`.
- Tokens: login and refresh return `data.tokens.access_token` and `data.tokens.refresh_token`. Mobile uses the body mode and keeps the refresh token in secure storage. The web build uses the API's cookie mode: every request sends `X-Token-Transport: cookie` and `withCredentials`, so the refresh token lives in an httpOnly cookie and never reaches JavaScript.
- DTOs use snake_case keys globally (`build.yaml` sets `field_rename: snake` for `json_serializable`).

## Visual system

Shared visual pieces live in `lib/core/theme` and `lib/core/widgets`, and every screen uses them instead of picking colors or formats on its own:

- `FinanceColors` (a `ThemeExtension` registered by `AppTheme.light` and `AppTheme.dark`) holds the positive, negative and warning colors and one color per `CategoryGroup`. Negative is always the scheme's `error`. Read it with `FinanceColors.of(context)`.
- `MoneyText` shows an amount in cents with tabular figures, optionally signed (`+R$`) and colored by sign. Money on screen goes through it, never through a colored `Text`.
- `categoryVisual` (`features/entries/presentation/widgets/category_visuals.dart`) maps each category `key` to an icon and a group, the same way `categoryLabel` maps it to a name; unknown keys get a generic icon grouped by kind. `CategoryAvatar` draws it.
- `SkeletonList` is the loading state of list screens (it pulses unless the system disables animations) and `EmptyState` is the empty state, with an optional action.
- The app follows the system light or dark mode.

## Balance, income, expenses and projection

| Route | Page |
|---|---|
| `/` | Início: a month switcher and the result of the month as the hero (signed and colored, with income and expense bars and "Sobram/Faltam R$ X até dd/mm/aaaa"), tiles for the latest balance ("Saldo informado", or "Informar saldo" without one) and the projected balance at the end of the month, the negative months warning, "Para onde vai o dinheiro" (an `fl_chart` donut of the five heaviest expense categories plus "Outras", with the fixed and variable totals) and a one-line shortcut to the bills due in the next 7 days |
| `/balances` | Balance history; tap to edit, trash icon to delete after confirmation |
| `/balances/form` | Inform or edit a balance (`extra` carries the balance being edited); the amount may be negative and the date cannot be in the future |
| `/entries?month=YYYY-MM` | "Lançamentos": every entry of a month. Tudo / Receitas / Despesas filters the kind, and with Despesas the Todas / Fixas / Variáveis chips filter the nature. The totals follow the filter (in, out and result for Tudo; the total with the fixed and variable subtotals for expenses). Arrows move between months, swipe left deletes after confirmation, and the checkbox marks an entry as paid or received today or back to pending, updating the row in place |
| `/due` | "Vencimentos", opened from the home shortcut and from Mais: pending expenses grouped as overdue (up to 3 months back, in red), the next 7 days and later this month, each group with its total. The checkbox or a swipe to the right marks one as paid today |
| `/more` | "Mais": the signed in user, balances, the bills due, security, due-date alerts, the administration (admins only) and "Sair" |
| `/entry/expense`, `/entry/income` | New or edited entry. A new one starts with Despesa / Receita on top (switching clears the category and the installments), then the amount in large type, the categories as a grid of icons, fixed or variable for expenses (preselected by the category's `default_nature`), description, date and whether it was already paid. A new one can repeat in the following or previous months (2 to 36 times, this one included), every month, every 3 or 6 months or every year ("Frequência"), with a preview of the dates, and an expense can be a card purchase in 2 to 48 installments, entering the total and seeing the installment value |
| `/projection` | Projection for the chosen period (3M, 6M, 1A or Tudo, `ProjectionPeriod`; 1A by default, and Tudo sends `months=all` so the API projects through the last entry). A hero says how much will be saved or lost by the last month, with the projected closing balance and "Ver mais ›". `CashFlowChart` draws the income and expense bars, the balance line (green above zero, red below) and the zero line; tapping or dragging selects a month, shown in the readout above it, and the legend chips turn the series on and off (one always stays on). Below come the negative months banner and a compact month by month list (result badge and closing balance) that expands to income, expenses, the fixed and variable bar and the savings so far. Pull to refresh reloads. Without a balance it asks for one first |
| `/projection/details` | "Ver mais": receives the loaded `Projection` as `extra` (without one it goes back to `/projection`) and explains the period without a new request: a waterfall from the opening balance through income, fixed and variable expenses to the closing balance, the result of each month with the accumulated savings, the fixed and variable split (`fl_chart` donut) with monthly averages, the five expense categories that weigh the most (`expense_by_category`) and the months that spend more than they earn with their two heaviest categories |
| `/projection/simulate` | What-if simulation, opened by "Simular gasto" on the projection. Add up to 10 hypothetical expenses or income items with the entry form (`/projection/simulate/expense` or `/income`, the same form with "repetir" and "parcelada", returning an `EntryPlan` instead of saving). Each change calls `POST /projection/simulation` and shows the current and simulated lines on the chart, the closing balances at the end of the period, the difference and the negative months alert. "Efetivar" saves each item through `POST /entries` or `POST /entry_series` and goes back to a reloaded projection; a failure keeps the items not saved yet. "Descartar" saves nothing |

The signed in app is a `StatefulShellRoute` (`AppShell`) with five tabs in a `NavigationBar`: Início, Lançamentos, Investimentos, Projeção and Mais. Each tab keeps its own navigation stack and cubit; tapping the current tab again goes back to its root. On the first three tabs a floating button opens a sheet with "Despesa", "Receita" and "Informar saldo". Forms and the other pages open above the shell. When a page saves something (a form returns `true`, an entry is deleted or marked as paid), it calls `FinanceChanges.notify()`, and `ReloadOnChange` makes every tab reload quietly (`load(quiet: true)` keeps the current content instead of showing the skeleton), so the home, the lists and the projection stay in sync.

Income and expenses share the same list and form: `MonthEntriesCubit` loads every entry of the month (`GET /entries?from&to`, with `kind` only when the repository is asked for one) and filters by kind and nature on the device, and the texts that differ use ICU `select` messages on the kind in `app_pt.arb`. `DueCubit` loads the pending expenses for the Vencimentos page, and `HomeCubit` builds the home summary from the month entries, the expense categories, the next 7 days and the projection.

A repeated entry is created with `POST /entry_series` (`EntryRepository.createSeries`), which generates one entry per month, or one every `interval_months` months (`Recurrence.interval`, `RecurrenceInterval` 1, 3, 6 or 12); entries of a series show a repeat icon. Tapping or swiping one asks "Só este", "Este e os seguintes" or "Todos da série" (`askEntryScope`), and the answer travels as `scope` on `PATCH` or `DELETE /entries/:id`. The form opens with an `EntryEdit` (entry and scope) as `extra`; outside "Só este" it says which entries change, hides "já paga" and sends neither `status` nor `paid_on`, and for installments it locks the amount, since the API answers `installment_amount_locked` otherwise. Marking as paid uses `EntryRepository.markPaid` (`status` and `paid_on` only). Installments use the same endpoint with `kind: installments` and `total_cents` (`EntryRepository.createInstallments`); the API splits the total and the leftover cents go to the first installment, and each one shows a card icon and its position ("Sofá 3/10") from `series_position` and `series_count`. The negative month warning comes from the projection's `alerts`.

The projection comes from the API's `GET /projection` (`ProjectionRepository`), including `savings_cents`; the app never recomputes balances. Chart values are converted to `double` only for drawing. `CashFlowChart`, `WaterfallChart` and `MonthlyResultChart` are `CustomPainter`s; their scales (nice axis steps, bar bands and the month under a finger) live in `lib/core/charts/chart_scale.dart` (`ValueScale`, `BandScale`), so the math is unit tested and the painters only draw.

Amounts are integer cents end to end (`amount_cents` in the API, `int` in the app); `Money` formats and parses BRL text without `double`. A received income or paid expense is sent as `status: paid` with `paid_on` equal to its date. Category names come from the API in English and are shown in Portuguese by `key` (`categoryLabel`).

## Investments

The Investimentos tab shows the family's FIIs and stocks from the API's portfolio (lar-em-dia-api README features 21 and 22). The app never recomputes positions: averages, costs, gains and the monthly evolution come from `GET /portfolio` and `GET /portfolio/history`.

| Route | Page |
|---|---|
| `/investments` | The net worth as the hero, with the contributed amount, the gain in R$ and % and the realized profit (only after a sale), the Renda × Crescimento bar, a 12-month evolution chart that opens `/investments/history`, and the positions with the Todos / Renda / Crescimento filter (ticker, name, shares, average price, latest quote with its date and gain %). Without transactions it explains the tab and offers "Registrar compra" and "Já tenho investimentos", which opens the buy form with a hint to use the broker's quantity and average price and with "Descontar do saldo" off |
| `/investments/new` | Register or edit a transaction (`extra` is an `InvestmentFormArgs`: the transaction being edited, a preselected asset and the shares held per ticker). The asset is searched in the catalog (`GET /assets?q=`, 300 ms after the last key and from 2 characters, `AssetSearchCubit`). Buy and sell ask for shares, price per share and fees, and "Descontar do saldo" / "Somar ao saldo" shows the amount that becomes an `investment_contribution` expense or an `investment_redemption` income. A split or reverse split is entered as a ratio ("A cada 1, passa a ter 2") and `SplitRatio` sends the difference in shares, as the API expects, from the shares held today; a bonus takes the shares received. The goal (Renda or Crescimento, FIIs default to Renda and stocks to Crescimento) is asked only on the first buy of a ticker. Editing keeps the kind and edits the quantity |
| `/investments/assets/:ticker` | The asset (type, sector, quote and date), the latest CVM monthly report of an FII (book value per share, P/VP, shareholders, equity), the distributions of the last 24 months (net value per share, JCP net of 15%, record and payment dates; manual ones open the form and the menu deletes them), the position (shares, average price, cost, market value, gain and realized profit), the goal toggle (`PATCH /investment_positions/:ticker`) and the transactions, newest first; tapping one edits it and the menu deletes it after confirmation. A refused deletion shows why (`insufficient_quantity`) |
| `/investments/history` | Net worth and contributed amount month by month since the first transaction (`EvolutionChart`, `fl_chart` like the projection chart) with the table of months below |
| `/investments/income` | Passive income from `GET /portfolio/income`: the 12-month monthly average, the months received and the forecast as bars, and each asset's 12 months and monthly forecast. The tab shows a "Renda passiva" card that opens it once there is any income; a failed income call only hides the card |
| `/investments/distributions/new` | Record or edit a stock dividend or JCP by hand (`extra` is a `DistributionFormArgs`: the ticker and the distribution being edited): kind, record date, payment date (not before the record date) and the gross value per share with up to 8 decimals (`PerShare.parseE8`). Only stocks of the portfolio offer it; FII income comes from CVM |

Every investments page ends with the same footer: the numbers come from the user's own transactions, they are not investment advice, quotes come from B3 and the registry from CVM open data (ODbL). Per-share values come as integers in hundred-millionths (`average_price_e8`) and are formatted by `PerShare.formatE8` (`lib/core/money/per_share.dart`) without `double`; gain percentages are integer basis points (`PerShare.basisPoints`). A transaction that touches the balance clears `FinanceCache`, and every page that saves calls `FinanceChanges.notify()`, so the home, the entries and the projection reload with the new expense or income.

In the projection, each month carries the forecast distributions after the current month (`investment_income_cents`, already in the income), the portfolio value and the total net worth. The "Incluir proventos" switch appears when there is forecast income and is remembered in `SharedPreferencesAsync` (`PrefsProjectionPreferences`); switching it off removes that income client side (`Projection.withoutInvestmentIncome`), so the cached projection and the `meta.projection` returned after each change stay valid.

## Emergency reserve

The emergency reserve (lar-em-dia-api README feature 23) lives under the Investimentos tab: a "Reserva de emergência" card at the top of the tab (also on an empty portfolio) and below the indicators on Início opens `/investments/reserve`. The app never computes yields, income tax or suggestions: it shows what `GET /reserve` and `GET /reserve/projection` return, and never names a product, bank or security.

| Route | Page |
|---|---|
| `/investments/reserve` | The net total as the hero with gross, yield and estimated tax; the suggestion ("6 meses dos seus R$ 3.100 de custos fixos") or the user's own goal with the coverage bar and "Ajustar meta" (1 to 24 months, or an amount; `PATCH /reserve`); the discreet `below_suggestion` and `idle_money` notices; the accounts; and the gross and net projection for 1, 2 or 5 years with its assumptions (or "taxas ainda não carregadas" when `rates_as_of` is null). Without accounts it explains the reserve and offers "Informar minha reserva" |
| `/investments/reserve/accounts/new` | Create an account (name, kind, % of CDI only for CDB, annual rate only for fixed rate, the LCI/LCA exemption only for both) with an optional balance of today that becomes an anchor movement; with an account as `extra` it edits it |
| `/investments/reserve/accounts/:id` | The account's values and movements, newest first; tapping one edits it, the bin deletes it after confirmation (a refused deletion shows `insufficient_reserve`), and the menu edits or deletes the account with its linked entries |
| `/investments/reserve/movements/new` | Deposit, withdrawal or "Saldo atual" (anchor) with date and amount (`extra` is a `ReserveMovementFormArgs`); "Descontar do saldo" / "Somar ao saldo" creates the `reserve_deposit` / `reserve_withdrawal` entry and is hidden for anchors |

On Início the card shows the net total, the coverage and each account; with the `no_reserve` alert it invites the user to inform a reserve, and "Agora não" hides it for 30 days (`ReserveDismissal`, stored with `shared_preferences`). Without fixed expenses and accounts it does not appear. The Projeção tab adds a "Reserva" line to the month readout and details and "Saldo + reserva" under the hero from each month's `reserve_cents`; the cash-flow chart is unchanged. Rates come as integers (`_bps`, `_e8`) and coverage as `coverage_months_e2`, formatted by `Rates` (`lib/core/money/rates.dart`) without `double`. Every reserve page ends with the disclaimer that the numbers are educational, computed from the user's data, not investment advice, and that rates come from the Central Bank (SGS).

## Authentication

| Route | Page |
|---|---|
| `/login` | Email and password; moves to `/two-factor` when the account has 2FA, and offers a new confirmation link when the email is not confirmed |
| `/two-factor` | TOTP or backup code for the login challenge (only reachable from the login) |
| `/register` | Sign up with the terms and privacy consents, then `/check-email` |
| `/check-email` | Resend the confirmation link |
| `/confirm-email?token=` | Link from the confirmation email; confirms and signs in |
| `/unlock?token=` | Link from the "account locked" email; unlocks and signs in, or asks for the 2FA code |
| `/forgot-password`, `/reset-password?token=` | Password recovery (the reset link comes by email) |

`SessionCubit` is the single source of truth for the session (`unknown`, `authenticated`, `unauthenticated`). It restores the session on start through `POST /auth/refresh`, and the router redirects on every change: unknown shows the splash, signed out users only reach the public pages, signed in users go home. When a refresh fails, `AuthInterceptor` clears the tokens and `SessionEvents` signs the user out.

The API email links point to the web routes above (`FRONTEND_URL` in the API). Deep links for the mobile apps come later.

### Sign in with Google

When the build gets `--dart-define=GOOGLE_CLIENT_ID=<web client id>`, the login and sign-up pages show "Continuar com o Google" (`GoogleSignInSection`); without it nothing changes. `GoogleSignInGateway` wraps `google_sign_in` 7: on the web it passes the id as `clientId` and shows Google's own button (`renderButton`, the only way to get an ID token there); on Android and iOS it passes it as `serverClientId`, so the ID token's audience is the same web client, and opens the system account picker. Every sign-in event's ID token goes to `POST /auth/oauth/google`. When the API answers `validation_failed` on `accept_terms` (a new account), the app asks for the terms and privacy consents and retries with the same token. A 2FA account continues to the code page. The API must list the same web client id in `GOOGLE_CLIENT_IDS`.

The deploy passes `STAGING_GOOGLE_CLIENT_ID` or `GOOGLE_CLIENT_ID` (repository variables) to the web build, and the Android workflow passes `GOOGLE_CLIENT_ID`. In Google Cloud, the web client lists the staging and production origins, and an Android client registers `dev.trita.laremdia` with the SHA-1 of the Play app signing key and of the upload key.

Accounts created with Google have no password: "Conta" reads `password_set` from `GET /me`, hides enabling 2FA for them and confirms "Excluir conta" with a fresh Google ID token (`id_token` in `DELETE /me`). With 2FA on, the code is used, as before.

## Account

| Route | Page |
|---|---|
| `/account` | "Conta": two-step verification status and remaining backup codes, with enable, disable and "new backup codes". Disabling and new codes ask for the current password and, when 2FA is on, a code (`DELETE /me/two_factor`, `POST /me/two_factor/backup_codes`). Disabling is hidden when 2FA is mandatory (admins). "Excluir conta" warns that the data is gone for good, asks for the password and, when 2FA is on, a code, sends `DELETE /me` (the API anonymizes the account) and signs out |
| `/account/two-factor` | Enrollment: the current password (`POST /me/two_factor/setup`), then a QR code and the secret to copy, then the 6-digit code (`POST /me/two_factor/enable`), and finally the 10 backup codes, shown once, with a copy button |

| `/account/notifications` | Due-date email alerts (`GET/PATCH /me/notification_settings`): on or off, and when to warn, from the due date itself to 7 days before. Changes save right away |
| `/unsubscribe?token=` | Target of the link in the alert email. It posts the token to `/me/notification_settings/unsubscribe` and confirms, signed in or not (the router never redirects it) |

"Segurança" on the Mais tab opens `/account`, and "Alertas de vencimento" opens the alerts. After enabling or disabling 2FA, the session user is updated so the rest of the app sees the new 2FA state without a new sign-in.

`TimeZoneSync` (started in `main.dart`) reads the device time zone with `flutter_timezone` whenever a user signs in or the session is restored, compares it with `time_zone` from `GET /me` and sends `PATCH /me` when they differ, so the API emails the alerts at 8h local time. Failures are ignored and retried on the next sign-in.

`DueRemindersSync` (started in `main.dart` only on Android and iOS, never on the web or in the demo) schedules local notifications for the bills of the next 30 days whenever a user signs in or the session is restored. It reads the same preferences as the email (`/me/notification_settings`), loads the expenses of this month and the next one, and keeps the pending ones due between today and 30 days ahead (`DueReminders.plan`). Each gets a reminder at 9h on the alert day (the due date minus the chosen days), alerts already in the past are skipped, and at most 60 are kept because iOS caps pending notifications at 64. `LocalNotificationsScheduler` cancels the previous reminders, asks for the notification permission (Android 13+ and iOS) and schedules each one in the device time zone with an inexact alarm, so no exact-alarm permission is needed. Signing out cancels them. With the alerts off nothing is scheduled. Reminders are recomputed only when the app opens, so a bill paid or added later updates them on the next launch.

Native setup: `AndroidManifest.xml` declares `RECEIVE_BOOT_COMPLETED` and the plugin's scheduled and boot receivers (reminders survive a reboot), `android/app/build.gradle.kts` enables core library desugaring, and `AppDelegate.swift` sets the `UNUserNotificationCenter` delegate so iOS also shows a reminder while the app is open.

| Route | Page |
|---|---|
| `/admin/users` | Users list: exact email search (names are encrypted in the API, so they cannot be searched), All / Active / Deactivated filter, "load more" paging (25 per page), and badges for admin, deactivated, locked and 2FA |

Only admins see the "Administração" section on the Mais tab (with "Gerenciar usuários", "Métricas de uso" and "Categorias"), and the router sends anyone else from `/admin` back home (the role comes from `/me` and is re-checked by the API on every request). The API requires the admin to have 2FA; without it the list answers `two_factor_setup_required` and the admin enables it on the Security page. Deleting an account is irreversible and stays out of the app. The demo build has no administration.

## Demo build

`--dart-define=DEMO=true` builds an app that needs no API: both Dio clients get `DemoAdapter` (`lib/demo`) as their `HttpClientAdapter`, an in-memory fake of the Lar em Dia API in the spirit of Ember's Mirage. Everything above the adapter is the real app (repositories, DTOs, `AuthInterceptor`, refresh, error codes).

```bash
flutter run -d chrome --dart-define=DEMO=true
flutter build web --release --no-web-resources-cdn --dart-define=DEMO=true
```

- `DemoServer` answers login, refresh, logout, `/me`, categories, balances and entries (CRUD, filters, paging, the API's validation codes), `POST /entry_series` (recurring, monthly or in fixed months, and installments) and `GET /projection` (with accumulated savings, negative months, alerts, `months=all`, `last_entry_month` and `expense_by_category`), `POST /projection/simulation` (the same validation by position, computed on a copy that is thrown away) with the API's rules, and the `scope` of `PATCH` and `DELETE /entries/:id` (`only_for_single_entry`, `installment_amount_locked`, day shift, recount and removal of an empty series). `DemoInvestments` answers the catalog (`/assets`, twelve real tickers with made-up quotes), the transactions with the API's validation codes (`unknown_asset`, `only_for_trades`, `insufficient_quantity`) and the `debit_balance` entry, `/investment_positions/:ticker`, `/portfolio` and `/portfolio/history`; `DemoReserve` answers `/reserve`, `/reserve/projection`, `/reserve_accounts` and `/reserve_movements` with a simplified calculation (a fixed 13.75% Selic, weekdays as business days, the same FIFO lots, anchors and regressive income tax as the API) and adds `reserve_cents` to the projection; `DemoLedger` follows the API's `PositionLedger` rules (weighted average with fees, sales at the average, corporate events change shares and not cost). Email flows answer success without sending anything. `/me/two_factor` keeps 2FA in memory: it checks the demo password, accepts any 6-digit code (a real TOTP check would need the secret on the device) and returns fixed backup codes. `/me` keeps the time zone and `/me/notification_settings` the alert preferences in memory; the unsubscribe link always answers `invalid_unsubscribe_token`, since the demo sends no email.
- `DemoSeed` creates the demo family relative to today: a balance on the first day of the month, two years of salary and fixed and variable expenses created as recurring series, a fridge in 10 installments and an English course in 24, the 13th salary every December and a trip that keeps the balance below zero for a few months. Entries due up to today are paid. Its portfolio has two years of monthly buys of FIIs (Renda) and stocks (Crescimento, with TAEE11 in Renda) and one sale, none of them in the balance. Its reserve has a Tesouro Selic account and an idle checking account, so the coverage, `below_suggestion` and `idle_money` show up, and three past months of fixed expenses feed the suggestion.
- The login page shows a demo notice with the account filled in (`DemoSeed.email` / `DemoSeed.password`). Data lives in memory, so reloading the page starts over.
- The demo uses hash URLs (`/#/projection`), so the web build opens from any address without server rewrites.

## Deploying the web app

The web build runs on the same server as the API, behind the API's kamal-proxy, so the app and the API share one registrable domain (the refresh cookie is `SameSite=Strict`). `Dockerfile` copies `build/web` into `nginx:1.28-alpine` with `deploy/nginx.conf`: every unknown path falls back to `index.html`, so path URLs work; `index.html`, `flutter_bootstrap.js`, `flutter_service_worker.js`, `manifest.json` and `version.json` are served with `no-cache`, so an installed PWA picks up a new version on the next launch; `/up` answers the proxy health check. Every response carries the security headers in `deploy/security-headers.conf` (CSP, HSTS, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`), and `server_tokens` is off. The deploy action fills the API origin into the CSP with `tool/prepare_web_headers.sh deploy/security-headers.conf "$API_BASE_URL"`. A new external service (another font host, analytics, a payment widget) must be allowed in that CSP, or the browser blocks it. `.dockerignore` sends only the build and the nginx configuration. `config/deploy.yml` builds from the local directory (`context: .`), because `build/web` is not committed.

`.github/workflows/deploy.yml` runs the CI (reusable through `workflow_call`) and then deploys through `.github/actions/web-deploy`. Nothing deploys on a push: a version tag (`1.0.0`, no `v`) goes to **production** (`kamal deploy`), only if the tagged commit is on `main`, and creating the tag is the approval, as in the API. **Staging** only runs by hand: Actions, Deploy, Run workflow on `main`, choosing `staging` (`kamal deploy -d staging`). Ticking `setup` runs `kamal setup` instead, for the first deploy; production runs by hand only with `setup`, so a normal production deploy always needs a tag. A job is skipped while its server is not configured (`STAGING_DEPLOY_HOST`, `DEPLOY_HOST`). The action builds the web app on the runner with `--dart-define=API_BASE_URL` set to the environment's API, so arm64 servers get their image through QEMU quickly, because the image only copies files. Images go to `ghcr.io` with the workflow token.

Repository variables for staging: `STAGING_DEPLOY_HOST`, `STAGING_DEPLOY_SSH_USER` (default `root`; `ubuntu` on Oracle Cloud), `STAGING_DEPLOY_ARCH` (default `amd64`), `STAGING_APP_HOST` (the app's host name, which must also be in the API's `CORS_ORIGINS` and `FRONTEND_URL`) and `STAGING_API_BASE_URL` (for example `https://staging-api.example.com/api/v1`). Production uses the same names without the prefix: `DEPLOY_HOST`, `DEPLOY_SSH_USER`, `DEPLOY_ARCH`, `APP_HOST` and `API_BASE_URL`.

Repository secrets: `STAGING_DEPLOY_SSH_PRIVATE_KEY` and `STAGING_DEPLOY_SSH_KNOWN_HOSTS`, and `DEPLOY_SSH_PRIVATE_KEY` and `DEPLOY_SSH_KNOWN_HOSTS` for production. `tool/deploy_key.sh staging|production HOST` (OpenSSH and `gh` logged in) generates a deploy key just for this repository, stores both secrets without printing the private key, and prints the public key to append to `~/.ssh/authorized_keys` of the deploy user and the host key fingerprint to compare with `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` on the server. The server itself (Docker, firewall, kamal-proxy) is prepared by the API's setup run, so set the API up first. Staging and production can share a server: their services (`laremdia-web-staging`, `laremdia-web`) sit behind the same kamal-proxy under different hosts.

## Publishing on Google Play

The Android application id is `dev.trita.laremdia` (permanent once published). Release builds are signed with the upload key from `android/key.properties` (`storeFile`, relative to `android/`, `storePassword`, `keyAlias`, `keyPassword`; git-ignored) or, when it is absent, from `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`. Without either, a release build fails instead of falling back to the debug key, so use `flutter run` (debug) on devices. Google Play App Signing re-signs the bundle with Google's key, so a lost upload key can be reset in the Play Console.

`tool/android_keystore.sh [KEYSTORE_PATH] [OWNER/REPO]` (needs `keytool` and `gh` logged in) generates the upload key at `~/lar-em-dia-upload.jks` by default, asks for its password without echoing it, stores `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` as repository secrets and prints the key's SHA-1 (for the Android OAuth client). It never overwrites an existing file. Keep the `.jks` and its password outside the machine.

The `Android` workflow (`.github/workflows/android.yml`) never runs on its own, because the app is not cleared for the Play Store yet: run it by hand from a version tag (Use workflow from, Tags), which must be on `main`. After the CI it builds a release app bundle against the production API (`API_BASE_URL` and `APP_HOST` variables), with the tag as the version name and the run number as the version code, so codes never repeat, and keeps `app-release.aab` as a build artifact to upload in the Play Console. The CI does not build Android, to save Actions minutes; `test/deploy/android_test.dart` checks the signing configuration and that the `INTERNET` permission lives in the main manifest, not only in debug.

## Search engines and link previews

Flutter draws the app on a canvas, so search engines only read what `web/index.html` carries outside it: the title and description, a canonical URL, Open Graph and Twitter Card tags for link previews (`web/og-image.png`, 1200x630), JSON-LD describing the app as a free `WebApplication` in `FinanceApplication`, and a short `<main id="landing">` text about the app that is removed on Flutter's `flutter-first-frame` event, so it doubles as the splash screen. `web/robots.txt` and `web/sitemap.xml` list the home page.

These files hold the placeholder `__SITE_URL__`. Before the build, the deploy action runs `tool/prepare_web_build.sh web https://APP_HOST true|false`, which replaces it with the environment's URL. Production passes `true`. Staging passes `false`, which turns the robots meta tag into `noindex, nofollow`, drops the sitemap and its `robots.txt` line, and keeps crawling allowed so search engines can see the `noindex`. Local and CI builds keep the placeholder.

### Legal pages

`web/privacy.html`, `web/terms.html` and `web/account-deletion.html` are plain HTML (no Flutter), so stores, Google's OAuth consent screen and search engines read them. They are listed in the sitemap and linked from each other. The sign-up consents open them through `openSitePage` (`lib/core/links/site_pages.dart`, `url_launcher`), which resolves the page against `SITE_URL` (passed by the deploy action as `https://APP_HOST`) or, when it is empty, against the current web origin. Builds for Android must pass `--dart-define=SITE_URL=https://APP_HOST`. The policy describes what the API actually stores; update it together with any change to the personal data the API keeps or to the services it uses.

After the first production deploy, add the app's domain to Google Search Console and submit `https://APP_HOST/sitemap.xml`.

### Content pages

Free tools and guides in plain HTML bring search traffic that the Flutter canvas cannot: `web/guias.html` (index), `web/calculadora-fim-do-mes.html`, `web/calculadora-juros-compostos.html`, `web/planilha-orcamento-familiar.html` and the `web/guia-*.html` guides. They share `web/conteudo.css`, end with a call to action that opens the app at `/`, and carry a canonical URL, Open Graph tags and JSON-LD (`Article` for guides, `WebApplication` for calculators) with the `__SITE_URL__` placeholder. `tool/prepare_web_build.sh` replaces it in every `web/*.html` and, on staging, turns every page's robots tag into `noindex, nofollow`.

The calculators run in the browser and send nothing. Their logic lives in ES modules under `web/js/` (`money.js` parses and formats amounts in integer cents, `fim-do-mes.js` and `juros-compostos.js` compute, `graficos.js` draws SVG charts without a library, `dica.js` shows chart tooltips, and `pagina-*.js` wire each page). The CSP only allows scripts from the site itself, so pages load them with `<script type="module" src="js/...">` and never use inline scripts or CDNs. Their tests use Node's test runner:

```bash
node --test 'test/web/*.test.mjs'
```

`web/planilha-orcamento-familiar.xlsx` is generated by `python3 tool/generate_budget_sheet.py` (needs `openpyxl`) and committed; run it again after changing the script.

To add a page: copy an existing guide, change the title, description, canonical, `og:url` and JSON-LD, link it from `guias.html` and from related pages, and add it to `web/sitemap.xml` and to `contentPages` in `test/web/content_pages_test.dart`.

## Quality

```bash
dart format --output=none --set-exit-if-changed lib test
flutter analyze
tool/test.sh
node --test 'test/web/*.test.mjs'
```

`tool/test.sh` runs `flutter test --coverage` with one test file per CPU at a time (Flutter's default is half the CPUs; `TEST_JOBS=2 tool/test.sh` chooses another number) and then `tool/check_core_coverage.sh`. To run a single file, use `flutter test test/path/to/file_test.dart`; the lib/core check only makes sense for the whole suite.

GitHub Actions runs all of them, plus a web build, on every pull request and on pushes to `dev`, in parallel jobs: `analyze` (format, analyze and the web content scripts), `test` split into `TEST_SHARDS` shards (`tool/test_files.sh INDEX COUNT` gives each shard a share of the test files, since `flutter test --total-shards` splits tests but still compiles every file in every shard), `coverage` (merges the shards' lcov files with `tool/merge_coverage.sh` and enforces lib/core coverage) and `build_web`. Changing `TEST_SHARDS` also needs the matching `matrix.shard` list.
